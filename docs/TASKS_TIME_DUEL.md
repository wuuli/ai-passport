# Time Challenge Development Tasks

## Delivery baseline

Implement [the approved game direction](PRD_TIME_DUEL.md) in five sequential tasks. Two agents share one AI Passport and compete in time-sense training. The game remains Time Challenge; do not add fictional missions, pairing, progression, or another game name. Keep the existing browser prototype as the visual review reference.

The first device version now includes the portable core, timestamped input, Chinese LVGL screens, device-sized pixel artwork, AI practice, and optional audio. The user authorized direct device installation. Implementation, automated checks, and physical acceptance are tracked separately below.

## TD-01 implementation contract

- Use integer microsecond timestamps supplied by the caller, round each estimate to milliseconds, and compare absolute errors. This is a scoring resolution, not a claim of 1 ms physical accuracy.
- Draw targets from 1.0 through 3.0 seconds in 0.5-second steps. Ties preserve the target and score and alternate the starter without advancing the scored round.
- Keep all state in one fixed-size caller-owned structure; no allocations, tasks, I/O, ESP-IDF, or LVGL dependencies.
- `duel_clock_init` starts at the home screen. `duel_clock_handle` accepts OK, periodic TICK, HOME cancellation, and a home-only mode toggle. Its boolean result means the visible game state changed, not that every internal timestamp stayed unchanged on false.
- Timestamps must be nonnegative and processed in order. Capture hardware timestamps before queuing. Snapshot the batch time before draining input, then submit that timestamp as TICK; never take a fresh timestamp after draining, which could overtake a concurrently queued press. A tick older than an already handled press is safely ignored. Process each input once and reject stale timestamps rather than silently changing measured time.
- An unfinished attempt stops at exactly target + 3 seconds, even if the polling tick is late. A late OK stops that attempt only; it must not also confirm handover or advance settlement. Accepted OK presses have a 200 ms debounce window.
- AI practice always starts with the human. Independent seeded random streams control targets and AI error; AI does not inspect the human estimate. Use Gaussian error with sigma = 0.12 x target, clamped to 220 ms through target + 2900 ms.
- AI wait lasts at least 1100 ms. When both attempts finish, SEALED waits indefinitely for OK; score and winner are not computed yet. Confirmation settles exactly once and starts ROUND_END. After 1500 ms, or an OK skip, it opens RESULT. The numeric result waits indefinitely for OK. Ticks never skip this result page or automatically begin another round.
- `duel_clock_view` is the UI boundary. It shows the target during handover and masks it during timing. SEALED exposes neither outcome nor numeric results and preserves the prior score. ROUND_END exposes the confirmed winner but still masks estimates/errors. Only RESULT and MATCH_WIN expose those numbers. Do not build labels directly from the internal model.
- Handover OK starts timing directly; there is no second readiness screen. Both estimates stay hidden. Match victory returns home after 3500 ms or OK, with a fresh OK at home required for the next match.
- HOME cancels an incomplete or completed match, retaining mode and random-stream progression. A mode toggle only works at home. No persistent player history or capability ranking is stored.

## Integration constraints

`main.c` now captures timestamps in the button callback and queues events without blocking. One LVGL timer drains the queue before ticking the game, keeping UI ownership and timeout ordering explicit. Screen-generation tags reject input left over from another page. Queue overflow cancels the match and asks the user to restart rather than fabricating a result. This routing change also needs regression checks on the retained hardware demos.

The new page explicitly selects Noto Sans SC subsets for Chinese. The [asset inventory](../assets/README.md#time-duel-artwork) records the font license, regeneration command, and 186,880-byte constant RGB565 image budget. Source PNGs are not runtime dependencies. Other demos retain their shared theme; the new page has a non-overlapping top-right battery indicator and an unavailable state.

Firmware UI access belongs to the LVGL task or an explicitly locked context. Audio and battery I/O use one application-lifetime 3072-byte-stack worker, which never holds a UI pointer. A single-slot overwrite mailbox delivers the latest sound state, preventing stale queued music from restarting after mute. The 32-byte portable synthesizer mixes an original melody/bass loop and six short cues into one 256-byte PCM buffer; it does not allocate or retain an entire recording. Leaving the page invalidates queued audio by generation and stops battery polling; an in-flight cue checks cancellation between 128-sample chunks. UI animations are deleted with their objects. No page-owned timer or callback survives teardown. Other demos retain their original screen theme and menu entry points.

The menu initially selects Challenge; OK enters the game. On the game home screen, UP changes duo/AI mode and DOWN toggles music and cues (on by default at volume 75/100). OK performs the displayed action. Holding OK for one second exits to the retained hardware menu; this is the firmware container boundary rather than the browser's home-only return. The core also supports HOME cancellation for input loss. After 60 idle seconds outside timing, the game dims to 15% and stops music; the next press wakes it and restores sound without playing a turn. The bootloader's five-second UP hook is unchanged.

The LVGL host test additionally checks unchanged pixels outside the battery label, no repeated flush for identical values, and preserved object/animation state. ## Physical feedback and refinement

The user reported that the first installed version played normally. This confirms basic physical playability, not every acceptance case. Their three requested refinements are implemented: original music plus button cues, direct timing from handover, and return home before another match. The first-to-three rule is unchanged. The browser preview now follows these refinements and the later sealed-confirmation flow, using firmware-derived artwork and separately labeled frozen example screens. Browser checks do not replace physical acceptance.

The initial refinement gate passed on 2026-09-06: application 1,801,568 bytes; merged image 1,867,104 bytes. Only the application at `0x10000` was updated after checking that the partition table matched the installed one. USB write hash verification passed. Startup again reported Display, Button, Audio, and Battery ready. The existing bootloader and all data/protected regions were left unchanged.

Updated core tests cover direct handover, both timed/manual return home, and a separate debounced restart from home across all 32 scored-match paths. Audio tests cover music looping, mute, all six cues, cue preemption, chunk independence, output bounds, and silence after the 24 ms start cue. Core and audio sanitizer tests pass. The user subsequently reported hearing audio but finding it too quiet, and requested explicit round-result confirmation. That revision raised default volume to 75/100 from 40/100 and made both round celebration and detailed results wait for OK, with one-hour idle host checks. The later clarification below supersedes that round-page sequence; I2S buffering means host silence is not proof of zero acoustic latency.

The previous volume/manual-confirmation version also passed the complete gate: application 1,801,536 bytes, merged image 1,867,072 bytes. Application-only USB write hash verification and all four peripheral startup checks passed. It includes the input-batch timestamp protection. The user subsequently reported good overall playability and sufficient button volume, but asked for stronger background music and confirmation before the winner is shown.

Current refinement: retain three separate pages (sealed results, round celebration, numeric results). Confirmation precedes the winner announcement and score update; the 1.5-second animation then opens the result automatically, while the next round remains manual. Music PCM amplitudes increase by 40% (about 2.9 dB); output volume stays 75/100 and six cue-waveform hashes match the pre-change baseline. Host tests pass for hidden results/prior score before confirmation, no idle reveal, celebration timing/skip, ties, AI, one-time scoring, unchanged cues, and silent timing. The complete ESP-IDF 5.5.3 gate passed for this refinement: application 1,801,792 bytes, merged image 1,867,328 bytes. A fresh read of the connected device's partition table matched the build. Only the application at `0x10000` was written; its USB hash verification passed and Display, Button, Audio, and Battery initialized successfully. The corrected UI fixtures show the prior score while sealed and the updated score only after confirmation. Latest host UI checks passed for 810 renders and 30 teardown cycles. Physical confirmation of the new reveal flow and background-music balance remains pending.

Next: complete the remaining physical acceptance matrix, especially held-button behavior and the final music balance, and restore and verify the official Recovery image through an authorized process. Release-build, USB-write, and publisher checks alone do not close those hardware gaps.
