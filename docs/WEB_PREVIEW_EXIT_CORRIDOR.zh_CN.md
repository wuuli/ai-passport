# 8号出口固件网页预览

主[预览](http://127.0.0.1:8098/)通过 WebAssembly 运行当前固件的游戏与渲染代码。请先启动下文的本地服务；直接用 `file://` 打开无法加载 WebAssembly 模块和素材。此预览替代独立 JavaScript 原型；早期 JavaScript 原型运行时已停用归档，角色烘焙工具与帧包校验测试继续保留。

## 声音

固件和网页共用 `main/corridor_sound.c`：轻微通风底噪、根据玩家实际位移触发的脚步（包含自动拐角），以及走到最终出口后的一小段通关尾音。停步和原地观察不触发脚步；异常种类、判断对错都不选择提示音。标题页保持安静。声音实时合成为 16 kHz 单声道 PCM，不增加录制音频素材。

固件适配层把声音快照交给现有后台 I/O 任务；按键和 LVGL 回调不写入 PCM。网页在用户操作后启用声音，区分待启用与已开启状态，并提供声音开关和音量滑块。电脑端单独调整播放增益（默认 40% 对应 4 倍，最高 10 倍；40% 保持原来滑块满格时的响度），共用原始 PCM 不变。固件在 Corridor 后台输出任务中仅施加一次带饱和保护的 6 倍增益，对应网页 60% 的数字幅度，编解码器音量仍为 75%。这不代表电脑与设备扬声器的实际听感响度一致；Time Duel 的输出不变。游戏输入也会恢复预览的焦点状态，避免内嵌浏览器遗漏焦点事件后一直静音。失焦、隐藏标签页、暂停评审及离开页面都会取消已排程音频；恢复时不补播历史脚步。浏览器 PCM 一致性不能证明真机音量、编解码延迟、帧率或内存余量，这些仍需实机验收。

主机检查覆盖行走／拐角触发、观察不出脚步、重开、静音历史事件、通关与网页退出。原生与 Wasm 的 112,000 个 PCM 采样完全一致。合成器与位移跟踪共占 80 字节，不含任务、消息队列和 PCM 缓冲。电脑端已接受音量条 60% 的响度；硬件时序和实体扬声器听感单独验收。

已安装归档（2026-09-29）：`build/firmware/0af8d8336e49fffb5c1d2cc8a830cd079a04f41a2c34d9af9f269160005248b1/`；完整镜像 SHA-256 `0af8d8336e49fffb5c1d2cc8a830cd079a04f41a2c34d9af9f269160005248b1`；配套 ELF SHA-256 `13b4fc1e67ae73708fc7ea89e2c52874902da646d5ef0330c431eb4f494fcf4d`。应用 1,507,440 字节，完整镜像 1,572,976 字节。Build PASS；Host tests PASS；Device tests PASS 仅覆盖下文有时限的 USB 自动场景。完整门禁使用仓库默认配置及 ESP-IDF 5.5.3。三个分段写入哈希全部通过，启动 ELF 前缀 `13b4fc1e6` 一致。未写入 NVS、PHY、身份及恢复区域。本轮未提交、推送或发布。2026-09-30，用户在整体真机试玩后确认声音没有问题。待验证：仪器级声学延迟、物理开关消抖边界与长期负载测试。

### 真机音频调度验收（2026-09-29）

被否决的候选版在游玩时出现七次空闲任务看门狗告警。匹配 ELF 后，部分采样落在 LVGL 刷新空转等待中；当时内部堆剩余 126,624 字节。证据指向 CPU 调度饥饿，而非内存分配失败。BSP 现通过 DMA 完成信号量阻塞等待；音频任务优先级为 5，高于 LVGL 的 4，写 I2S 时仍会阻塞。实测含诊断日志的栈余量仅 420 字节，因此将该任务栈从 3,072 增至 3,584 字节；PCM 与帧缓冲大小不变。

最终安装镜像执行了 130 秒 USB 测试，15 条命令全部收到确认，覆盖进入、行走、停步、左右观察、两处自动拐角停步、正确跨通道升至 1，以及三次返回标题／重新进入。20 个音频统计窗口测得最长供给间隔 1,649 微秒，最长合成耗时 431 微秒，最长写入等待 14,935 微秒。稳态供给为每秒 15,993–16,033 个采样；初始补充缓冲的窗口可能高于标称 16,000。音频任务最小栈余量为 932 字节。没有出现看门狗、panic 或音频写入失败。

停步区间的脚步计数保持不变（11、22、29、40），后续统计窗口回归轻微环境声，没有反复触发脚步。每次返回标题均记录音频空闲并停止游戏帧生成。稳态游玩为 9.68–11.00 fps，内部堆剩余 125,992 字节，最低 115,792 字节，最大连续块 106,496 字节。这些仅是有时限场景的测量，不是性能保证。计时测试结束后，另行读取 USB 截图，确认走廊与 HUD 正常显示；随后让设备停在静音标题页并释放串口。没有录制声学输出，因此这些检查不能证明所有可听爆音已经消失。 2026-09-30，用户完成真机试玩并确认声音正常；本次听感验收为用户观察，不是声学仪器测量。

### 先在网页验收声音

电脑端播放在安装前通过验收，但随后用户反馈旧 `cf5f4aec...` 真机候选版仍有延迟和爆音。旧版仅在标题页观察 12 秒的启动检查没有覆盖实际游玩，不能代表声音验收通过。上文标识的是现已安装的调度修复版。

在原有游戏页面展开「声音试听」，可分别播放进入／行走／停步／返回的完整流程、静止环境声、行走后停步、自动拐角、原地观察和最终出口六段固定样例。每段都驱动独立的真实 C 游戏与声音合成器实例，将 PCM 按 60% 参考增益编码成 16 kHz 单声道 WAV。试听会暂停行走，不改变玩家位置或分数。原生音频控件独立于实时排程播放生成的片段，也可下载反复试听。参考片段固定为 60% 增益，不跟随实时游戏音量条；同一时间只播放一条声音通路。

主机测试检查参考 PCM 无削波、WAV 编解码采样一致、原地观察无脚步、拐角自动停止与通关尾音结束；还重复执行 30 轮进入／行走／停步／返回流程，检查进入后及时出声、停步后回归环境底噪、开始界面持续静音；这些检查不能证明音色合格。实时排程现已保持剩余不足 5 ms 时的相邻片段时间连续，预排程窗口为 100 ms，并在 `getAudioState()` 暴露欠载次数与最长空隙。这修复了已复现的网页排程空隙，不代表已定位真机声音问题。

修订后的 C/Wasm 声音去掉了持续的 100 Hz 灯管嗡声，并压低通风噪声。60% 参考增益下，静止 RMS 从 -32.7 降到 -45.7 dBFS，六段样例均无削波。用户补充说明持续声出现在人物停步后，与此前一直开启的环境声相符，但仅凭这点不能解释真机爆音。真机调度证据已单独记录在上文。

## 共用代码与素材

- `main/corridor_game.c` 和 `main/corridor_render.c` 原样编译。三键行走、圆弧拐角、斜向可见物件对中、按进入侧判定、走错归零和连续八次通关均使用同一份 C 实现。
- 网页加载同一份 312,689 字节的 `commuter-device.bin`；调色板、人物查表和告示数据由固件 include 编入。墙面采用浅灰纯色，保留距离明暗和踢脚线，不使用墙砖查表或 PNG 图集。横向连接通道墙面（`side >= 2`）暗一级以保证拐角明暗对比。原生 C 与 Wasm 像素级一致性已通过；64 组同视点接缝与双外拐角对比回归通过。包含此拐角区分优化的当前固件已于 2026-09-27 安装到真机，并通过串口截取到开机直达标题页的画面。
- 生成的 `presentation.json` 提取 16px 正文与四字形 30px 标题字体，并与 `demo_corridor.c` 校验标题／状态文字。Canvas 外壳按 RGB565 量化展开索引画面，以原生 240×320 绘制暗色开场、日光色通关界面和 HUD。开场按实体位置标明顶部键、中部键、底部 OK 键，并说明拐角自动转向停步；开头与结尾的主操作均位于 y=252、返回提示位于 y=287。主操作在 800ms 内渐显一次后保持稳定。UI 调整不改变楼梯与出口渲染。
- `manifest.json` 保存源码与生成产物的 SHA-256；加载时核验 Wasm、界面数据和人物素材，静态门禁拒绝源码修改后未重建的旧产物。

薄层 C 桥接只暴露输入、推进、输出及显式评审样例。网页层处理指针／键盘、可见性、加载、显示和开发工具，不再独立实现游戏状态机。

## 运行与重建

本地预览检查需要 Python 3.10+、Node.js 18+ 和 C11 编译器。查看已生成的预览只需要现代浏览器及 HTTP 服务，无需 SDK。

```bash
python3 tools/serve_corridor_web.py --port 8098
# Open http://127.0.0.1:8098/
python3 tools/build_corridor_web.py --check
node tests/test_corridor_web.mjs
```

服务仅监听回环地址，只提供预览与素材子目录。端口已被占用时不要再启动第二个服务。

修改清单内的原生源码或素材后，使用官方 [WASI SDK](https://github.com/WebAssembly/wasi-sdk/releases) 重建（已验证 34.0）：

```bash
python3 tools/build_corridor_web.py --sdk /path/to/wasi-sdk
./tools/validate.sh --static
# Activate ESP-IDF 5.5.3 before the complete gate:
./tools/validate.sh
```

`corridor.wasm`、`presentation.json` 和 `manifest.json` 必须配套保存。运行库许可随模块保存在 `prototype/exit-corridor/firmware/`；人物来源见[素材说明](../assets/images/exit-corridor/README.zh_CN.md)。

## 操作与评审

UP／上箭头按下向左转 45°，DOWN／下箭头按下向右转 45°，短按 OK／空格／Enter 会从标题页进入，或在游戏中于松开时切换走停。长按 OK 一秒返回网页标题；同时仅接受一个按键。失焦、隐藏标签页和取消触摸均停止行走。

开发评审默认收起；展开时暂停并显示答案。可选择全部九种正常／异常场景、门楣正向与折返对照视角、用户反馈的 45° 海报位置、拐角及边界／最后一轮位置。继续观察恢复模拟，也可按 OK 开始行走。回到盲玩会从零开始，注入的样例不会带入盲玩。放大仅改变 CSS 显示尺寸。

自动拐弯过程中，OK 暂停／继续圆弧。左右键取消辅助并停止位移；目标朝向先取最近的 45° 方向，再叠加所按方向的转角，由相机缓动转向。按键瞬间的位置和显示视角不会跳变。普通手动转向仍是相对当前方向转 45°。

跨越通道边界时，游戏分数照常立即判定。左上角数字保留上一轮结果，等相机靠近中线并转向下一段走廊后才更新，避免先于场景内出口牌透露新编号。手动转向也能触发显示；显示后即使回头，数字也不会倒退。

## 走出通道

第八次正确判断进入 `EC_EXITING`（3），而不是直接进入 `EC_CLEARED`（2）。新通道保留跨界位置和拐角辅助，显示出口 8，并通向短楼梯与自然光。方向键仍转 45° 并停步，OK 切换行走。进度固定为 8，不再选择异常，回头不会触发新的判断。走上楼梯，再经过两米平台到达出口门口，才显示持续保留的通关面板；再单独按 OK 才开始停止行走的出口 0。这里是面向设备的“走出通道”体验适配，不是原版结尾的逐帧复刻。

快速受控评审可选正常场景加第 7 轮前方跨界，或红灯加第 7 轮后方跨界。按 OK 跨界，等待辅助拐角正对台阶停下，再按 OK 走出；途中随时可以暂停和观察。出口几何由同一套内存有界的 C 渲染器生成，不另分配帧缓冲或楼梯纹理。

## 验证与边界

2026-09-20 拐角复验通过可见网页控件检查了四个进入方向，停点分别为 (0.85, -26.8, 90°)、(-0.85, 2.8, -90°)、(0, 1.95, 0°) 和 (0, -25.95, 180°)，均位于下一段通道中心线上并面向该段。审查另复现了圆弧中途手动接管后朝向偏离网格的问题，已在共用 C 逻辑修正，并补充原生及 Wasm 回归测试。实体键时序与真机运动体感仍待硬件验收。

加入出口终段之前，2026-09-20 的受控网页验收确认了旧版即时通关面板、主动重玩和红灯前进的 7→0 失败。该历史检查不覆盖新增楼梯。真机专有的漏刷新另由 `tests/test_corridor_demo.c` 调用实际固件 tick 与 UI 桩覆盖，现包含出口段持续渲染和限帧时走到出口门口通关；Canvas 显示正常不能替代真机 LVGL 刷新验收。

2026-09-20 更新后的原生 C 与 Wasm 对照使用 5,729 条指令、163 个采样画面，包含 24 组拐弯中途暂停后接管、再从原地恢复辅助的用例。12,518,400 个索引像素中有 2 个不同，最大颜色通道差值为 2/255，状态最大误差为 1.20e-7。覆盖换轮、两个进入方向、可行走出口段与门口通关、转向、暂停和观察。这是采样等价检查，不代表所有可能操作都已穷尽。

网页交互验证确认：斜看海报转正后停在 X=0、Z=-20、90°；正常 7→8 通关及重玩；异常前进 7→0；异常折返 0→1。旧 WebGL 地址已加载共用固件预览。

新结尾已通过可见评审控件和真实按键验收：正常前进与红灯折返均进入出口 8，经辅助拐角后继续走到各自出口门口才通关。另行检查了楼梯中段 45° 观察、主动重玩后停在出口 0，以及错误前进的 7→0。默认桌面视口和 390x844 截图确认场景与三键无重叠。预览停在台阶前供用户验收。这些是受控样例，不是重新盲玩八轮。静态／主机测试和 ESP-IDF 固件门禁通过，渲染器 ASan／UBSan 检查通过。未刷写设备，楼梯真机帧率、体感与 RAM 余量仍待验证。

网页不模拟 ESP32 内存压力、SPI／DMA 时序、实体 ADC 去抖、LVGL 合成、电量或设备菜单。电量为 `--`，长按 OK 回到预览标题。网页循环最多提交 20 帧／秒，性能显示明确标注非真机测量；原生帧缓冲对比不包含 Canvas HUD 合成。网页构建不修改或刷写设备固件。

## 本地性能模拟的范围

Wasm 预览共用玩法、渲染和音源，设备与浏览器适配层分别运行。它不运行设备的 FreeRTOS、LVGL、SPI/DMA 或 I2S。因此，仅靠浏览器 CPU 限速或降低帧率，并未暴露显示刷新忙等导致的真机音频断供。

[Demo 到真机 SOP](development/engineering/application-demo-to-device-acceptance.zh_CN.md)现已在玩法和真机验收之间加入资源压力关。[`tools/game_resource_stress.py`](../tools/game_resource_stress.py)建模固定优先级、可抢占 CPU 工作、释放 CPU/忙等的显示等待、按墙钟时间完成的 DMA、不可抢占停顿、PCM 消耗及额外内存预算。它是确定性负载实验，不是 ESP32/FreeRTOS 模拟器。

```bash
python3 tools/build_corridor_web.py --check
node tests/test_corridor_audio.mjs
node tests/test_corridor_resource_stress.mjs \
  --output-dir /tmp/corridor-resource-stress-acceptance
```

游戏专用检查用实际 Wasm 执行三组可重复场景：进入/行走/停步/观察/标题/重进、自动拐角/停步、出口完成。导出带时间戳的音频/渲染开关及 Wasm、manifest 哈希，再用通用模型运行[部分测量的设备配置](../tests/fixtures/corridor_resource_profile.json)。停步保留实际环境声开关；返回标题停止模型需求及游戏 PCM。这是基准负载：模型 CPU 延迟不会反馈到 C 玩法运动或界面中。

配置记录已验收的 130 秒真机样本和完整固件哈希。渲染 CPU 使用最大的窗口平均值（50,133 微秒），不是逐帧最坏情况测量；音频合成使用观测到的 431 微秒最大值。完整刷新时间（50,337 微秒）被保守地再次算作阻塞等待，不表示纯 SPI 时间。110 毫秒帧周期是实验目标。PCM 余量使用 6 x 240 描述符结构，实际可播放容量及初始预填充仍是假设。内存取已运行游戏的 125,992 字节空闲及 106,496 字节最大连续块，仅计算额外分配，实验预留为 100,000 字节。这些是场景输入，不是统一板卡配置，也不模拟碎片。

本地集成验收的三组正例都通过，模型断供为零；十二个反例检出了旧忙等/低优先级配置造成的延迟或断供、120 毫秒不可抢占停顿、过大的额外帧缓冲，以及未完成校准。汇总明确区分 `modelRegression: PASS`、`wasmWorkloadIntegration: PASS` 与 `calibratedResourceAcceptance: NOT RUN`、`hardwareAcceptance: NOT RUN`。`--require-calibrated` 会拒绝这份部分校准配置。该关放行前，应分别测量有效 PCM 余量、显示等待，获取适用的渲染尾部耗时，并用独立真机样本对照模型预测。不能仅凭模型断供推断实际爆音。

实际总线时序、缓存/Flash 影响、分配失败恢复、堆碎片、扬声器音质和持续负载仍需要独立测试与真机验收。压力命令不会重建、刷写或发布固件。

## USB 真机验收

游戏固件在物理 USB 串口上接受以换行结尾的 `FAP_KEY_V1 LEFT`、`RIGHT`、`OK`、`BACK` 命令，每行都需带完整的 `FAP_KEY_V1` 前缀。它们分别表示顶部键、中部键、短按底部 OK 键和长按 OK。这些命令进入与物理按键相同的事件队列，只有 LVGL 分发器会访问游戏 UI。无效命令被忽略，队列溢出会停止移动。此开发接口不模拟物理开关消抖或人的按键时序。

执行有时限的进入、行走、停下、观察、拐角、返回标题和重新进入流程，同时采集 `game_audio` 的供给速率、最长间隔、合成与写入耗时、栈余量、PCM 峰值及游戏帧率和堆内存。截图传输会扰动时序，必须与音频计时测试分开。USB 测试无法确认扬声器的实际听感。
